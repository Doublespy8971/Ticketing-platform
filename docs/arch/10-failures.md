## 12. Failure Scenarios Table

| # | Failure Scenario | Expected System Behavior | How We Will Test It |
| :--- | :--- | :--- | :--- |
| **1** | **Flash-Sale Contention Spike**: 5,000 concurrent buyers send `POST /api/v1/reservations` for the exact same `seatId` at `drop_time`. | Exactly **1** request succeeds with `201 Created` (`status = 'HELD'`). The remaining **4,999** requests are rejected in `< 20 ms` at the Redis `hold_inventory.lua` gate (returning `"SEAT_TAKEN"`) with `409 Conflict` (`SEAT_ALREADY_TAKEN`) without opening PostgreSQL transactions. `inventory_db` contains 1 row in `reservation_items` for that `seat_id`. | k6 load test (`500 VUs` with synchronized barrier) + JUnit 5 `CountDownLatch(200)` integration test asserting `COUNT(*) = 1` on `reservation_items WHERE status IN ('HELD', 'CONFIRMED')`. |
| **2** | **PostgreSQL Failure After Redis Lua Hold**: `hold_inventory.lua` succeeds in Redis (`"HELD"`), but the subsequent `inventory_db` transaction throws `SQLException` or connection timeout. | `inventory-service` catches the exception, rolls back the PostgreSQL transaction, and executes `release_inventory.lua` inside its `finally` block (matching `reservationId`), immediately deleting `seat:{eventId}:{seatId}`. Returns `500` to client; subsequent buyer can immediately reserve the seat. | Testcontainers + Toxiproxy test that injects a TCP reset on `inventory_db` right after `hold_inventory.lua` returns `"HELD"`, asserting `GET seat:{eventId}:{seatId}` in Redis is `nil` immediately after the failed HTTP call. |
| **3** | **Hard JVM Crash (`SIGKILL`) Between Redis Lua Hold and PostgreSQL Commit**: `inventory-service` pod is killed after `hold_inventory.lua` sets Redis keys, before the `finally` block or PostgreSQL commit can run. | No `reservations` row or `outbox_events` row exists in `inventory_db`. The orphaned `seat:{eventId}:{seatId}` key in Redis automatically expires after its `660s` safety-net TTL (`EX 660`), releasing the seat with zero manual intervention and zero phantom orders. | Integration test that executes `hold_inventory.lua` directly without committing to PostgreSQL using a shortened test TTL (`3s`), verifying a subsequent reservation request succeeds once the Redis TTL elapses. |
| **4** | **Early Checkout Before `inventory.seat.reserved` Is Consumed**: Client calls `POST /api/v1/orders/{orderId}/checkout` 10 ms after receiving `201 Created` from `inventory-service`, before the 200 ms outbox poller and `order-service` consumer materialize the `orders` row. | `order-service` sees zero rows for `orderId` in `order_db.orders`, rolls back the `IN_PROGRESS` `idempotency_keys` entry, and returns `409 Conflict` with `errorCode: "ORDER_NOT_READY"` and header `Retry-After: 1`. Client retries 1 second later with the same `Idempotency-Key` and receives `202 Accepted`. | Integration test that pauses the `order-service` Kafka listener container (`ContainerLifecycle`), calls `POST /api/v1/orders/{orderId}/checkout` to assert `409 ORDER_NOT_READY` + `Retry-After: 1`, resumes the listener, and retries with the same `Idempotency-Key` to assert `202 Accepted`. |
| **5** | **Late Payment vs. Hold Expiry Race**: Checkout is submitted at `t = 580s`; at `t = 600s` `inventory-service` expires the hold (`HELD -> EXPIRED`) and another user buys the seat; at `t = 602s` `payment-service` emits `payment.succeeded` for the first user. | `inventory-service` consumes `payment.succeeded`, locks `reservations` `FOR UPDATE`, sees `status = 'EXPIRED'`, refuses to mark the seat `SOLD`, and emits `inventory.seat.confirmation_rejected`. `order-service` transitions the first user's order to `REFUND_PENDING` and emits `order.refund.requested`. `payment-service` refunds the payment and emits `payment.refunded`, moving the order to `CANCELLED_REFUNDED`. | Integration test using `MOCK_PAYMENT_MIN_LATENCY_MS=4000` and `POSTGRES_HOLD_TTL_SECONDS=2`, verifying User A's order ends in `CANCELLED_REFUNDED`, `payments.status = 'REFUNDED'`, and User B's concurrent hold on the released seat succeeds. |
| **6** | **Unpaid Hold Expiry via `1000 ms` PostgreSQL Sweeper**: A held reservation reaches `expires_at` (`600s`) without payment across multiple running `inventory-service` replicas. | Within `1000 ms` (`HOLD_EXPIRY_SWEEP_INTERVAL_MS=1000`), the PostgreSQL sweeper selects the expired hold using `WHERE status = 'HELD' AND expires_at <= NOW() ORDER BY expires_at ASC LIMIT 500 FOR UPDATE SKIP LOCKED`, commits `reservations.status = 'EXPIRED'`, `seats.status = 'AVAILABLE'`, and `inventory.reservation.expired` in `inventory_db` **first**, and only after commit executes `release_inventory.lua` to delete the `660s` Redis seat lock. | Integration test with `POSTGRES_HOLD_TTL_SECONDS=2` and `HOLD_EXPIRY_SWEEP_INTERVAL_MS=1000`, asserting that an unpaid hold is transitioned to `EXPIRED` in `inventory_db`, deleted from Redis via `release_inventory.lua`, and transitioned to `CANCELLED_EXPIRED` in `order_db` within 2 seconds of `expires_at`. |
| **7** | **Redis Seat Lock Safety-Net TTL vs. PostgreSQL Sweeper Delay**: At `t = 600s`, a hold reaches `expires_at`, while a transient database hiccup delays the `1000 ms` PostgreSQL sweeper by 3 seconds (`t = 603s`). | Because Redis `seat:{eventId}:{seatId}` has a `660s` safety-net TTL while PostgreSQL `expires_at` is `600s`, Redis keeps rejecting new buyers with `409 SEAT_ALREADY_TAKEN` between `t = 600s` and `t = 603s`. At `t = 603s`, the `1000 ms` PostgreSQL sweeper commits `EXPIRED` / `AVAILABLE` in PostgreSQL first, and only then invokes `release_inventory.lua`. | Integration test asserting `TTL seat:{eventId}:{seatId}` is `> 600` immediately after reservation creation and verifying via spy/interceptor that `release_inventory.lua` is invoked strictly inside `afterCommit()` of the `1000 ms` PostgreSQL sweeper transaction. |
| **8** | **Outbox Poller Failure Mid-Batch or Crash Before Marking Row Published**: The single active poller (`pg_try_advisory_lock` on a fixed lock ID held on a dedicated connection) fails to send the 15th row in a 100-row batch, or crashes right after receiving a broker ack for a row before executing `UPDATE outbox_events SET published_at = NOW()`. | Because the poller sends sequentially, waits for each broker ack, and marks each row published immediately after its ack, rows 1..14 are already marked published; at row 15 the poller stops the batch immediately so rows 15..100 are not sent out of order. If it crashed between a single row's broker ack and its `UPDATE`, the newly elected leader re-sends that single row on the next 200 ms cycle, and downstream consumers deduplicate the `eventId` via `processed_events` (`ON CONFLICT DO NOTHING`) or Redis `SET notif:dedup:{eventId} "1" NX EX 604800`. | Integration test that injects a broker send failure on the 3rd outbox row (verifying rows 1..2 have `published_at IS NOT NULL`, rows 3..5 remain `NULL`, and row 4 is never sent before row 3) plus a duplicate `eventId` delivery test across all consumers. |
| **9** | **Duplicate HTTP Checkout / Hold Requests**: Client retries `POST /api/v1/reservations` or `POST /api/v1/orders/{orderId}/checkout` 3 times with the same `Idempotency-Key` due to mobile network packet loss. | The first request executes the mutation and stores `status = 'COMPLETED'`, `response_status`, and `response_body` in `idempotency_keys`. Subsequent requests return the exact cached HTTP status and JSON body with header `X-Idempotent-Replay: true`. Reusing the key with a different body returns `422 IDEMPOTENCY_KEY_PAYLOAD_MISMATCH`. | JUnit 5 MockMvc / RestClient test sending 5 identical requests with the same `Idempotency-Key` (asserting `X-Idempotent-Replay: true` on calls 2..5) and 1 request with a modified `seatIds` list (asserting `422`). |
| **10** | **Transient Downstream Consumer Error & Notification Failure Handling**: `order_db` experiences a 3-second connection hiccup while `order-service` consumes `inventory.seat.reserved`; or `notification-service` encounters a delivery error on `order.confirmed`. | For stateful Java services (`inventory-service`, `order-service`, `payment-service`), the local transaction rolls back and Spring Kafka forwards the message to `<topic>-<group>-retry-0` (`2s` backoff) and `-retry-1` (`10s` backoff). For Go `notification-service` (which has no retry or DLT topics), it logs the failure at `ERROR` level, increments `ticketing_notifications_sent_total{status="FAILED"}`, and does not forward to any topic. | Testcontainers + Toxiproxy test injecting a 3s connection cut on `order_db` (verifying recovery via `-retry-0` / `-retry-1`), plus a `notification-service` test injecting a notifier failure and asserting `ticketing_notifications_sent_total{status="FAILED"} == 1` with zero messages published to Kafka. |
| **11** | **Poison-Pill Message / Unrecoverable Consumer Error**: A malformed JSON record or unknown event schema version is published to `order.events`. | Stateful Java consumers (`payment-service`) fail deserialization/validation and route the record to `order.events-payment-service-order-cg-dlt` (`ticketing_kafka_consumer_dlt_total` increments). Stateless Go `notification-service` logs the error, increments `ticketing_notifications_sent_total{status="FAILED"}`, and commits the offset without forwarding to any topic. | Integration test publishing raw invalid JSON bytes to `order.events`, asserting the record arrives on `order.events-payment-service-order-cg-dlt`, `ticketing_kafka_consumer_dlt_total == 1`, and `notification-service` logs the failure and increments its failure metric without forwarding. |
| **12** | **Redis Full Restart / Flush During Active Sale**: Redis container restarts and loses in-memory keys while seats are `HELD` and `SOLD` in `inventory_db`. | Next `POST /api/v1/reservations` call receives `"EVENT_NOT_CACHED"` from `hold_inventory.lua`, triggering the `inventory-service` rewarm job to restore `event:{eventId}:drop_ts`, `HELD` seat locks with `TTL = seconds_remaining_until_expires_at + 60`, and `SOLD` seats with no TTL from `inventory_db`. Even if a race occurs during cache warming, PostgreSQL `UPDATE seats ... WHERE status = 'AVAILABLE'` and `idx_reservation_items_active_seat` block any duplicate hold with `409 SEAT_ALREADY_TAKEN`. | Chaos test executing `FLUSHALL` on Redis mid-load test, verifying `0` duplicate reservations in `inventory_db.reservation_items`, `HELD` seats restored with `TTL = remaining + 60`, and `SOLD` seats restored with `TTL = -1` (no expiration). |
